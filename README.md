# RazorRecover — AI Revenue Recovery System

**Razorpay AI Buildathon — Track 03: AI Revenue Recovery**

RazorRecover detects revenue at risk from failed payments, diagnoses the failure, estimates recovery probability, selects a safe recovery intervention via an AI agent, enforces deterministic guardrails before any action executes, and measures the resulting recovered revenue.

> **All transaction data is SYNTHETIC.** This project does not use real Razorpay customer data. The dataset is generated by a reproducible seeded generator.

---

## Problem

Merchants lose revenue from payment failures, checkout abandonment, recurring payment failures, temporary failures, insufficient funds, expired mandates, and repeated failed attempts. Manual recovery is slow, inconsistent, and risky.

## Solution

RazorRecover automates the recovery pipeline:

```
Transaction Data → Revenue-at-Risk Detection → Recovery Prediction → AI Recovery Agent
→ Deterministic Policy/Guardrail Engine → Approved Recovery Tool → Payment Simulator
→ Recovery Result → Audit Trail → Business Metrics
```

**Critical principle:** the AI agent never has unrestricted authority over financial actions. The LLM recommends an action from a closed set; a deterministic policy engine approves or rejects every action before execution. Money calculations, retry limits, cooldowns, idempotency, and audit logging are all deterministic.

## Business Value

- **Recovered revenue** — automatically retries and re-engages failed payments that would otherwise be lost.
- **Safe automation** — guardrails prevent double-charging, over-retrying, and acting on terminal states.
- **Explainability** — every decision has a concise reason, confidence, and audit trail.
- **Human-in-the-loop** — high-value and low-confidence cases escalate to a human reviewer.
- **Measurable impact** — batch evaluation reports precision, recall, F1, ROC-AUC, recovery rate, and false-intervention cost.

## Architecture

See [docs/architecture.md](docs/architecture.md) for the full architecture diagram and module breakdown.

### Where AI is used

- **Recovery probability prediction** — interpretable ML model (logistic regression / gradient boosting) estimates P(successful recovery | transaction context).
- **Recovery agent** — LLM receives structured transaction context and selects an action from a closed set, with confidence and expected recovery.
- **Failure diagnosis** — deterministic rules first, ML classification where it adds value.

### Where AI is NOT used

- **Policy enforcement** — 100% deterministic. The LLM cannot override guardrails.
- **Money calculations** — deterministic integer-cent arithmetic.
- **Transaction state** — deterministic, verified via idempotency keys.
- **Retry limits / cooldowns** — deterministic counters and timestamps.
- **Audit logging** — append-only, deterministic.

## Dataset

A reproducible seeded generator produces 50,000–100,000 synthetic transaction records with realistic distributions across payment methods, failure codes, customer histories, and subscription states. See [scripts/](scripts/) and [docs/architecture.md](docs/architecture.md).

## Evaluation Methodology

Reproducible train/validation/test split. See [docs/evaluation.md](docs/evaluation.md) for the full methodology and actual metrics.

- **ML metrics:** precision, recall, F1, ROC-AUC
- **Business metrics:** revenue at risk, revenue recovered, recovery rate, false-intervention cost, escalation rate
- **Agent metrics:** valid action rate, invalid output rate, guardrail violation rate, correct escalation rate

## Guardrails

See [docs/security.md](docs/security.md) and [docs/design-decisions.md](docs/design-decisions.md).

- Never retry a payment that already succeeded
- Never retry beyond the configured maximum
- Never act during cooldown
- High-value transactions require human approval
- Low-confidence decisions require escalation
- API timeout requires state verification before retry
- Money-related actions require idempotency protection
- Every rejected action is logged

## Limitations

- Razorpay Test Mode integration is abstracted behind a provider interface; the default provider is a local simulator. Real Razorpay API calls require valid test-mode keys in `.env`.
- The ML model is interpretable (logistic regression / gradient boosting) — chosen for explainability, not peak accuracy.
- All data is synthetic.
